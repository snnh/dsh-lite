# Agent Note: 已构建 headless CLI 宿主的必需内存姿态性能 gate

Status: implemented

[English](2026-10-06-memory-posture-performance-gate.md) | 中文

## 问题

已启动 Harness 宿主的常驻集与空闲 CPU 曾被人工测量过多次，却没有任何东西守着它们。懒加载与客户端产物按需读取的工作把空闲常驻集从 266–275 MB 降到 236–240 MB；`--max-semi-space-size=4` 把同一宿主从 255.8 MB 降到 164.5 MB；一个已恢复的 Agent 在 127,400 事件的 Session 上保留了 26.1 MB 堆；空闲 CPU 约为每 10 s 一个 10 ms jiffy。每个数字都来自内存工作流计划中记录的人工运行，因此一次普通改动——一个新的即时 import、一个无上限的 cache、一个永不停止的计时器——就能把它们全部还回去，而所有功能测试仍然全绿，因为没有任何检查读取进程的常驻集或它的空闲 CPU。

测试进程无法提供这个读数。Vitest 的 loader、它的插桩、父进程自身的堆与历史，以及测试 harness 挂载的插件行，都属于在它内部测得的常驻集；而每会话数字需要一个已启动的宿主打开多个 Session 并在此后继续运行。增量还必须在被测区间两端各做一次收集：否则读数会把 Session 保留的东西与最近一次操作分配、尚未释放的东西混在一起。

## 决定

必需的 benchmark lane 运行 `benchmarks/memory-posture/memory-posture.bench.ts`。既有的 `test:bench` 命令负责构建它：`benchmarks/tsdown.config.ts` 新增一项 entry，把 `memory-posture.probe.ts` 与 `memory-posture.model.ts` 编译到 `benchmarks/.dsh-build/memory-posture/`，与该 lane 既有的 workspace library 和其他已编译 worker 并列。[Session 打开性能 gate](2026-09-04-session-open-performance-gate.zh.md)拥有该 lane、它的 `node 24 / benchmarks` job 以及外层 job 超时；本次改动给该 lane 增加一条被测路径，而不是第二个 job。

### 被测对象

被测对象是已构建的正式 `apps/cli` 入口（`apps/cli/lib/bin.js`）在纯 Node 的全新子进程里启动正式 `headless` profile（即无密钥的那个），绝不进入 Vitest 进程。一个 benchmark 自有的 `--patch` overlay 塑造这次启动，而不是重新拼装它：

- 它禁用两个一次性 runner 行 `headless-startup` 与 `headless-runner`，它们各自拥有一个 task 并随其退出；probe 取代它们成为进程生命期的拥有者。
- 它把 `session-persistence-jsonl` 指向该子进程私有的 Session 根目录并使用 Zstandard 压缩，因此不读取、也不写入任何环境中的 transcript。
- 它插入已编译的 probe 插件与一个 benchmark 自有的 model adapter。该 adapter 注册 Session 打开所需的 provider 路由，并在被测宿主真的请求它生成时抛错，因此一旦 profile 变化开始运行轮次就会立刻失败，而不是静默地测量另一条路径。

其余每个正式行都按用户启动时的样子挂载，包括 `apps/cli/src/bin.ts` 在 profile 工作之前启动的[常驻集策略](../../../../packages/util/memory/README.zh.md)。两个已编译插件都调用 `assertBuiltBenchmarkRuntime`，因此经 TypeScript loader 或从源码到达的运行会被拒绝，而不是去测量另一个 runtime。在子进程内部，probe 等待 launcher 提交的就绪信号（`appReady`）、静置、观测空闲常驻集、花掉一个空闲 CPU 窗口、打开这些 Session、在 stdout 写出一行 JSON 并退出；死线与判定归父进程所有。

每个子进程都获得私有的 `mkdtemp` home、workspace 与 agents home 根目录，以及自己的 Session 存储；suite 在开始取样前先用这些根目录做一次不计量的启动。这次预热是有承载作用的：某个 profile 的首次启动会创建 profile 目录并付出 Node 编译缓存，若把它算进任意一个样本，描述的就是这台机器的首次运行，而不是此后每次启动都持有的姿态。

### 三份预算

| 预算 | 上限 | 判定聚合 | 取样 |
|---|---|---|---|
| 空闲常驻集 | 400 MB | 样本中位数 | 3 个全新子进程，各自在就绪信号之后再静置 15 s 后取样 |
| 每会话常驻集 | 64 MB | 样本最大值 | 每个子进程 4 个 Session，各带 600 个已完成轮次 × 3,000 字符（约 1.8 MB 持久化日志） |
| 空闲 CPU | 500 ms（10 s 内单核的 5%） | 样本中位数 | Session 阶段之前的那个空闲窗口 |

上限是 `benchmarks/memory-posture/memory-posture.constants.ts` 中经审查的源码常量，没有环境变量覆盖，因为[benchmark 目录规则](../../../../benchmarks/AGENTS.md)要求预算由经审查的常量执行；改动预算就是评审者能看到的源码 diff。工作负载出于同样理由固定：合成历史由经审查的常量通过生产 Session append 路径与生产 assistant-stream 压缩生成，不读取任何录制 transcript、用户材料或环境仓库。

空闲样本会等过正式策略。`SETTLE_MS` 取 15 s，是因为该策略启动 10 s 后收集一次，跨这次收集读取会把启动留下的瞬态当成姿态的价格，而长跑宿主持有的是后者。等待以就绪为锚点，`readyMs` 会被报告，但没有任何东西执行它：就绪是启动时量，而启动耗时归计时 lane 所有。

每会话阶段先播种 Session，再为每个 Session 的正式 `ctx.agents.resume()` 打开定价，因此被测路径正是用户打开 Session 走过的路径——解析日志、恢复 Session、在正式 profile 自带 preset 行之上挂载 Agent。播种是测量区间之外的 fixture 工作：“before” 快照取自最后一个已播种日志关闭之后，并在 `--expose-gc` 下围绕一次事件循环让出做两次显式收集，因此增量是活跃宿主每打开一个 Session 保留的量，而不是编写日志的成本。判定用样本最大值而不是中位数，因为某个子进程可能在它的 resume 阶段把已释放页归还操作系统，中位数就会低报一个 Session 实际持有的常驻集。每会话阶段抛错时，它所在的用例会以记录下来的原因和已打开 Session 数失败，而不是靠一份残缺读数通过。

空闲 CPU 是 10 s 窗口内的进程 CPU——用户态加内核态——按中位数判定，同时以毫秒和内存工作流决策记录所用的 10 ms jiffy 报告，并与窗口长度、按单核百分比表示的预算以及用户态、内核态分量并列。

### 参考姿态

整份文件的一次运行，在本开发机（Node v24.18.0、16 CPU、已构建 CLI），两次完整运行复现：

| 测量项 | 观测值 | 预算 |
|---|---:|---:|
| 空闲常驻集，3 次样本中位数 | 197.6 / 197.7 MB（样本 194.2–198.1 MB） | 400 MB |
| 空闲 `heapUsed` | 42.2 MB | — |
| 空闲峰值 RSS（`maxRSS`） | ≈198 MB | — |
| 就绪（`readyMs`） | ≈443 ms | 不执行 |
| 每会话常驻集，中位数 | 10.9–12.2 MB | 64 MB |
| 每会话常驻集，最大值 | 11.1–16.2 MB | 64 MB |
| 每 Session 保留堆 | ≈3.3–3.4 MB | — |
| 4 个 Session 的常驻集增量 | 43.6–48.7 MB | — |
| 10 s 内的空闲 CPU | 0.5–0.8 ms，即 0 个整 jiffy | 500 ms |
| 整份文件运行时间 | ≈104 s | job 超时 |

每个判定的日志行都报告原始样本及其最小值、中位数、最大值，以及它所判定的聚合，并附带平台、架构、CPU 数、可用并行度与 Node、V8 版本，使一份读数可以与产生它的机器对照。上表的参考数字是供评审用的机器档基线，不是 CI 预期：没有任何预算会乘上或缩放到它们。

## 校准证据

这些上限是回归警戒线，不是紧凑预算，已记录的参考姿态远低于每一条。共享 CI 运行器在机器之间的波动大于懒加载工作赢得的约 40 MB，因此一个紧凑到能保护这点差值的上限会抖动，随后又会被习惯性地放宽。经审查的上限仍能拦住一个数量级的丢失——空闲常驻集涨到数百 MB、单个 Session 保留自身日志的一大部分——而更紧的机器档读数由评审者手工比较：懒加载工作前空闲 266–275 MB 对之后 236–240 MB，`--max-semi-space-size=4` 下 164.5 MB 对不开启时的 255.8 MB，以及一个已恢复 Agent 在 127,400 事件 Session 上保留的 26.1 MB 堆，全部引自 benchmark 自身校准块中内存工作流的人工测量。

benchmark 自带一个校准 `describe` 块，它钉住的是这个决定而不是一次测量：它断言已记录的参考姿态（空闲 152 MB、197.6 MB、240 MB；每 Session 9 MB、16.2 MB、26.1 MB；空闲 CPU 10 ms）在经审查的上限下通过，实质性退化（空闲 700 MB、每 Session 200 MB、10 s 内空闲 CPU 3,000 ms）失败，并且已记录的 +40 MB 懒加载退化按设计仍留在经审查的上限之内。今后改动某条上限或某个预算的聚合方式，也必须一并改动这些断言。

## 刻意排除的测量

- **长跑漂移。** 该 gate 只在一个有界样本里测量一次已稳定的姿态。缓慢泄漏、或数小时后才越过阈值的 cache 不在范围内，这里的一次通过读数从不声称不存在这类问题。
- **浏览器面。** 浏览器的内存归[前端性能预算](2026-09-06-frontend-performance-budgets.zh.md)所有。
- **模型生成。** 每会话阶段从不向 provider 请求补全；benchmark 自有的 adapter 只是让正式 Session 打开能解析到一条路由，一旦真的尝试生成它就会抛错。
- **就绪时间。** `readyMs` 报告为约 443 ms 且不被执行，因为启动耗时是计时 lane 的主题，姿态上限不得悄悄变成启动耗时预算。

## 考虑过的替代方案

**把这些用例加进 Session 打开 benchmark。** 拒绝：那个文件用自己已编译的 worker 与 fixture 根目录测量冷 Session 打开耗时，而姿态属于已启动宿主的稳态；把两者折进一个文件会让同一行判定同时拥有两个无关主题，而且姿态路径仍然必须启动正式 CLI。

**用 benchmark 自有的最小 profile 而不是正式 `headless` profile 启动宿主。** 拒绝：重新拼装出的近似物的常驻集不是正式启动的常驻集。该 gate 守的退化类别正存在于哪些正式行被即时加载，替换它们等于绕开移动过的那件事去测量。

**在进程内、在 Vitest worker 里测量这次启动。** 拒绝：loader、插桩、父进程的堆与历史，以及 harness 自己挂载的行都会进入读数；只有运行已构建 JavaScript 的全新子进程，数字才描述正式宿主。

**只采样一个长生命周期子进程并反复取值。** 拒绝：连续样本共享同一个堆、分配器 arena 与编译状态，因此无法报告样本间波动，而且一次糟糕的启动会污染全部判定而不是一个样本。全新子进程加私有根目录也把环境 profile 与 transcript 挡在读数之外。

**按接近参考姿态设置紧凑上限。** 拒绝：共享 CI 运行器的机器间波动超过懒加载工作赢得的约 40 MB，紧凑上限要么抖动，要么在没有证据的情况下被放宽。经审查的上限拦住数量级的丢失；机器档比较仍是评审动作。

**在 CI 中与历史 checkout 对比。** 拒绝：历史修订版需要独立安装，并固定它自己的运行器与 Node 版本，因此这种对比测到的环境变化和代码变化一样多。固定工作负载加经审查常量无需额外安装即可复现。

**每个预算都用中位数判定。** 拒绝用于每会话读数：某个子进程可能在 resume 阶段把页归还操作系统，中位数于是会低报真实的常驻集；该预算改用最大值，中位数仍留在日志里。

**在就绪之后立刻取空闲样本。** 拒绝：就绪触发时启动期工作仍在排空，而正式策略自己的收集落在 10 s 处，立即读取是在给瞬态定价。就绪之后再静置 15 s 读到的是宿主真正持有的姿态。

**允许环境变量覆盖，好让调试运行放宽预算。** 拒绝：[benchmark 目录规则](../../../../benchmarks/AGENTS.md)禁止性能预算由环境变量覆盖；被放宽的运行还会让“在 CI 通过”和“在本地通过”变成两种不同的说法。

**在同一个文件里也守长跑漂移。** 拒绝：数小时的 soak 不适合有界的 job，而且有界样本无法确立不存在泄漏；内存工作流的阈值策略仍是漂移机制。

## 后果

每个 pull request 的 benchmark job 现在会启动已构建 CLI 四次——一次预热启动加三个样本——并在 20 分钟的 job 内用约 104 s 跑完整份文件。作为交换，该 lane 得到了一条针对长跑宿主所持姿态的可执行警戒线、一个按已声明历史规模定价的每会话保留量，以及以内存工作流所用单位给出的空闲 CPU，全部基于正式启动而不是形状近似物。

该判定是警戒线，不是承诺：位于参考姿态与上限之间的读数是对机器或这次改动的评审信号，通过上限从不证明姿态良好。参考数字是供评审用的机器档基线；没有乘以任何时间系数，它们不是 CI 预期。

工作负载、静置时长、样本数与每个判定所用的聚合都是这个决定的一部分，而不是附带设置：改动历史规模或 Session 数会静默移动每会话预算的含义，改动静置或聚合会改变被认证的是哪份读数。Node、运行器或工作负载变化时，必须在同一改动中用同一路径重新采样并评审常量；修改业务实现时不得在没有新校准数据的情况下放宽上限。

该 gate 刻意不测长跑漂移、浏览器面、模型生成与就绪时间，也不新增任何生产导出：probe 与 model adapter 是通过正式 overlay loader 挂载的已编译 benchmark 自有插件，它们只通过已构建的 package exports 触达产品服务。
